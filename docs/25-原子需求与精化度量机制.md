# 25 — 原子需求与精化度量机制

本文档描述 Agile-SOFL Studio / `@agile-sofl/parser` / `@agile-sofl/editor-api` 中 **Hybrid 规格（`.asfl`）** 的精化模型：何谓**原子需求**、如何**度量精化程度**、**过程线与数据线**的二义性计数、**可审计精化步骤**，以及该机制与 Liu SOFL 方法、需求缺陷预防之间的关系。面向工具实现、科研实验与论文写作，可作为方法章节的权威对照。

相关文档：[01-Agile-SOFL-介绍.md](./01-Agile-SOFL-介绍.md)、[05-FSF-规约.md](./05-FSF-规约.md)、[07-语义分析.md](./07-语义分析.md)、[17-Informal与Hybrid规格编辑器设计.md](./17-Informal与Hybrid规格编辑器设计.md)、[15-Studio可视化编辑器.md](./15-Studio可视化编辑器.md)。

## 1. 问题背景与定位

### 1.1 经典 SOFL 与 Agile-SOFL

Liu 的 SOFL 方法采用 **Informal → Semi-formal → Formal** 三步演化；形式层以 **模块 + 条件数据流图（CDFD）+ 过程 pre/post** 组织系统。分解函数 \(f\) 将非底层过程映射到子 CDFD/子模块，直至**简单过程**可用 SOFL 语言完全规格化。

Agile-SOFL 在模块—过程—数据模型上引入 **FSF（Functional Scenario Form）** 与 **informal 原子谓词**，支持渐进形式化。本仓库约定：**源语言是 pre/post**；FSF 由 pre/post **推导**（见 [05-FSF-规约.md](./05-FSF-规约.md)），编辑器内部的 `FSF :` DSL 仅为兼容旧文件。

### 1.2 Informal 与 Hybrid 的分工

| 载体 | 角色 | 是否「分解到叶子」 |
|------|------|-------------------|
| **Informal（`.aspec`）** | 平行 Markdown 式需求：功能、数据资源、约束 | **否**。子功能通常折成**场景**（guard/outcome），不建立 CDFD 分解树 |
| **Hybrid（`.asfl`）** | 可解析、可检查的混合形式规格 | **是**。通过 `decom`、子 module、CDFD 自顶向下精化 |

Informal → Hybrid 的生成/合并建立 **traceability**；**原子化与二义性消减**仅在 Hybrid 侧通过工具义务与审计日志完成。

### 1.3 本机制不承诺的内容

精化度量基于 **实用静态检查**（语法、类型、结构平衡、informal 原子检测、场景划分启发式），**不是**完整形式化验证。原子需求表示「在当前方法下义务闭合、可签收为叶子」；**不保证**逻辑无误、Informal 无遗漏、或与实现语义等价。论文中应明确区分 **obligation closure** 与 **correctness proof**。

## 2. 原子需求（Atomic Requirement）

### 2.1 直觉定义

**原子需求**在 Hybrid 中对应一个 **叶子过程（leaf process）**：行为不再通过 `decom` 向下分解，而在该过程的 **pre/post（及由它们推导的功能场景）** 上用**可解析的形式谓词**说清；同时满足模块级 **CDFD 出现**、**类型闭合**等结构条件，并在审计日志中经 **`DeclareAtomic`** 显式声明。

带 `decom` 的 **复合过程（composite process）** 不是原子需求，而是精化树上的**中间节点**，其语义由子 module 的 CDFD 与过程集合实现。

### 2.2 结构原子（structurallyAtomic）

实现见 `packages/parser/src/refine/atomicity.ts`。对非别名过程，下列条件**同时**成立时记为结构原子：

| 条件 | 含义 |
|------|------|
| `!hasDecom` | 无 `decom:`，不再分解 |
| `informalAtomCount === 0` | pre/post（及仅在没有 pre/post 时的 `FSF :`）中无 `informal_text` 与自然语言 clause |
| `typesDefined` | 输入、输出、`ext` 类型已定义（含不允许仍为 `given` 等） |
| `scenarioCoverageComplete` | 由 pre/post 推导的场景划分完整（互斥且覆盖 pre 允许域，或含形式化 `others` 等规则） |
| `onCdfd` | 过程名出现在**本 module** 的 `cdfd` 块 `node` 声明中 |

代码中的合成条件：

```text
structurallyAtomic = !hasDecom && informalAtomCount === 0 && typesDefined
                     && scenarioCoverageComplete && onCdfd
```

### 2.3 声明原子（declared atomic）与状态枚举

结构原子尚不足以在审计意义上「签收」。`@agile-sofl/editor-api` 的 `buildRefinementState` 为每个过程计算：

| `status` | 条件 |
|----------|------|
| `open` | 非结构原子（仍有 decom、informal、场景/CDFD/类型等缺口） |
| `ready` | 结构原子，但日志中尚无成功的 **`DeclareAtomic`** |
| `atomic` | 结构原子 **且** 日志中存在针对该过程的 **`DeclareAtomic`** |

**论文表述建议**：*An atomic requirement is a leaf process that is structurally atomic, operationally atomic, and explicitly declared via an auditable refinement step.* 形式原子见本节；操作原子见第 11 节。

### 2.4 闸门（Studio 列表树中的 gate）

对叶子过程，Studio 精化树展开后可查看闸门。前五道与 `structurallyAtomic` 对齐；第六道是操作粒度（第 11 节）：

1. **decom** — 无分解  
2. **informal** — 无 informal 原子  
3. **types** — 签名与 ext 类型闭合  
4. **coverage** — 场景覆盖完整  
5. **cdfd** — 已在本 module CDFD 上  
6. **grain** — 操作粒度已闭合（`grainClosed`）

## 3. 双线精化（Process Line vs Data Line）

Liu 方法中 **过程分解** 与 **数据精化（retrieve / 抽象类型具体化）** 是两条线，工具**分开计数、分开展示**，不混在 CDFD 诊断里。

### 3.1 过程线（Process refinement）

- **载体**：过程、pre/post、FSF 推导、module 内 **CDFD**、`decom` 与子 module。  
- **诊断族**：`ASFL_CDFD_*`（图与模块成员一致、边界流平衡、条件节点出边等）、过程原子性相关计数。  
- **目标**：所有**期望叶子**达到 `status === 'atomic'`。

### 3.2 数据线（Data refinement）

- **载体**：module 内 **`refine` … `end_refine`** 块（`type T by Rep retrieve fn`）、`given` 类型、retrieve 函数体。  
- **诊断族**：`ASFL_DATA_*`（见 `packages/parser/src/refine/checkDataRefine.ts`）。  
- **开放义务**：操作精化（具体 post 经 retrieve 蕴涵抽象 post）第一期以 **`DischargeDataObligation`** 人工审查关闭，不内置定理证明器。  
- **目标**：`dataAmbiguity === 0` 且相关义务已在日志中 discharge。

### 3.3 精化完成度（Dual-line progress）

Studio 与 `formatRefinementDigest` 使用 **双线进度**：

- **过程原子率** `processRate = atomicLeaves / expectedLeaves`（在分解树根 module 上统计叶子总数与已 `atomic` 叶子数，见 `leafStats` / `dualLineProgress`）。  
- **数据释放率** `dataRate`：数据精化项中已 discharge 比例；无数据项且无空 module 时视为 1。  
- **粒度闭合率** `grainRate`：叶子过程中操作粒度已闭合的比例；`grainAmbiguity > 0` 时该率小于 1。
- **综合进度** `overall`：过程率、数据率与粒度闭合率的 **三线调和平均**（任一线为 0 则整体为 0）。

**无歧义签收（工具层面）** 当且仅当（见 `formatRefinementDigest` 文案）：

```text
processAmbiguity === 0
dataAmbiguity === 0
grainAmbiguity === 0
emptyModuleCount === 0
stubProcessCount === 0
```

（且通常要求无未审计的 informal 消失：`unloggedFormalizations === 0`。）

## 4. 二义性计数（Ambiguity Counting）

### 4.1 过程二义性 processAmbiguity

原始快照来自 `analyzeProcessAtomicity`：

```text
processAmbiguity =
  informalAtomCount
+ incompleteScenarioCount
+ openConditionCount
+ unbalancedBoundaryCount
+ undeclaredAtomicCount
```

| 分量 | 含义 |
|------|------|
| `informalAtomCount` | 全规格 informal 原子总数 |
| `incompleteScenarioCount` | 场景覆盖不完整的过程数 |
| `openConditionCount` | CDFD 中条件节点出边不足或未含 `others` 的个数 |
| `unbalancedBoundaryCount` | CDFD 边界流不平衡类诊断数 |
| `undeclaredAtomicCount` | **结构原子但尚未 DeclareAtomic** 的过程数（在原始计数中每个这样的过程 +1） |

**审计调整**：`buildRefinementState` 在展示用 `processAmbiguity` 时，对已 **`DeclareAtomic`** 且结构原子的过程从计数中扣除，并加上 **`unloggedFormalizations`**（见下）。

### 4.2 数据二义性 dataAmbiguity

来自 `checkDataRefine`：`given` 类型、缺失 retrieve、开放 operation-refinement 义务等项之和（详见 `DataRefinementReport.dataAmbiguity`）。

### 4.3 未记录的形式化 unloggedFormalizations

若用户在编辑器中**直接删除或改写** informal 原子而未提交 **`FormalizePredicate`** 步骤，则产生 **`ASFL_REFINE_001`**，且 **`unloggedFormalizations > 0`** 时过程二义性**不因文本变形式而下降**。这保证论文与实验中的 **可审计精化** 假设。

## 5. 可审计精化步骤（Refinement Steps）

### 5.1 日志位置

项目目录 **`.agile-sofl/refinement-log.jsonl`**：每行一条 JSON（`RefinementLogEntry`），含步骤种类、目标、前后内容哈希、前后 **processAmbiguity / dataAmbiguity**、informal 键集合变化等。

规格文本 **`.asfl`** 仍为状态源；日志**不**存 CDFD 布局坐标。

### 5.2 步骤种类（Hybrid）

| 步骤 | 作用 |
|------|------|
| `FormalizePredicate` | 将一处 informal 原子替换为形式谓词（唯一可审计地减少 informal 计数） |
| `DecomposeProcess` | 创建子 module、边界 port、空 CDFD，设置父过程 `decom` |
| `SetCdfd` | 写入/更新 module 的 `cdfd` 块 |
| `BalanceFlows` / `DefineType` / `BindConstraint` / `Extend` | 结构扩展或义务修复（计数变化依实现） |
| `DeclareAtomic` | 在结构原子 **且** 操作原子成立时签收叶子过程 |
| `ClassifyGrain` | 把叶子标成单一操作 `operation`，或仍是关注点 `abstract` |
| `ResolveVariation` | 把一条已抽出的变体标成 `scenario` / `child` / `waived` |
| `IntroduceRetrieve` | 数据线：引入 retrieve |
| `DischargeDataObligation` | 数据线：审查关闭义务 |

API：`applyRefinementStep`、`buildRefinementState`（`@agile-sofl/editor-api`）；Studio IPC：`applyProjectRefinementStep`（`refinementLog.ts`）。

### 5.3 Agent 与可视化

Studio **精化**侧栏提供 **列表式精化树** 与 **纵向精化树** 两种视图；对问题节点可右键触发 AI 精化工具（映射到上述步骤）。Agent 应优先 **`propose_refinement_step`**，而非绕过日志直接改谓词。

## 6. CDFD 与场景：两套「覆盖」

方法上需区分（论文中建议分节写清）：

1. **CDFD 条件节点**：架构级互斥出边（至少两条，含 `others`），检查数据在过程/存储间的路由。  
2. **过程 pre/post 功能场景**：行为级输入域划分，由 **FSF 推导** 检查 guard 互斥与在 pre 下的穷尽性。

二者**不合并**为单一检查；原子叶子应同时满足各自义务。

## 7. 精化树（Refinement Tree）结构

### 7.1 逻辑结构

- **根**：未被任何 `decom` 指向的 module（通常为 `SYSTEM_*`）。  
- **module 节点**：其下为该 module 内各 **process**。  
- **composite process**：有 `decom` → 子 module 子树（子 module 内再递归）。  
- **leaf process**：无 `decom` → 终端；颜色/状态反映 `open` / `ready` / `atomic`。  
- **缺口**：空 module（仅名字）、缺失的 decom 目标 module。

Informal 功能树**不**出现在此树上；仅 Hybrid 分解树。

### 7.2 Studio 可视化

| 视图 | 说明 |
|------|------|
| **列表式精化树** | 可展开 process/data/log 根；叶子下展示五道闸门与 informal 原子 |
| **纵向精化树** | 自上而下：SYSTEM → module → process → 子 module …；**绿色**表示已声明原子（`atomic`），**强调色/警告色**表示未闭合 |

实现：`atomicityTree.ts`、`refinementVerticalTree.ts`，组件 `AtomicityTree.vue`、`RefinementVerticalTree.vue`。

## 8. 与需求缺陷预防的关系

| 缺陷类型 | 机制如何提前暴露 |
|----------|------------------|
| 分解丢输入/输出 | CDFD 边界平衡、`ASFL_CDFD_BOUNDARY` |
| 分支遗漏/重叠 | 场景覆盖检查 + CDFD 条件出边 |
| 含糊自然语言残留 | informal 原子计数 + 必须 `FormalizePredicate` |
| 过早签收 | `ready` vs `atomic`；`DeclareAtomic` 门禁 |
| 抽象数据未具体化 | 数据线 `dataAmbiguity`、`given` / retrieve 检查 |
| 非审计改写 | `ASFL_REFINE_001` / `unloggedFormalizations` |

实验设计建议：对比 **有/无审计日志**、**有/无 CDFD 检查** 条件下，检出缺陷的数量与类型；以 `processAmbiguity`、`dataAmbiguity`、`dualLineProgress.overall` 作为 **因变量** 或 **过程指标**。

## 10. 论文写作可用的定义小结

**Definition (Structurally atomic).** A leaf process is *structurally atomic* iff it has no decomposition, its pre/post contain no informal atoms, its types and scenario partition are complete under the tool’s rules, and it appears on the module CDFD.

**Definition (Operationally atomic).** A leaf process is *operationally atomic* iff it is classified as one operation, it has no unresolved or missing-child variations, its name and description are not wider than the single effect observed in post, that effect is not `mixed`, and any variations marked `scenario` match the derived functional scenarios one-to-one.

**Definition (Atomic requirement).** A leaf process in a Hybrid specification is an *atomic requirement* iff it is structurally atomic, operationally atomic, and a `DeclareAtomic` entry exists in the refinement audit log.

**Definition (Refinement completeness).** A Hybrid specification is *refinement-complete* w.r.t. the tool iff process, data, and grain ambiguity counters are zero, no empty or stub processes/modules remain, and no unlogged informal formalizations or grain closures are pending.

**Remark.** Refinement-completeness implies reduced ambiguity and structural consistency obligations; it does not imply total correctness of the specification w.r.t. stakeholder intent. Operational atomicity makes Liu’s qualitative “simple enough” stopping rule auditable. It is an Agile-SOFL extension, not a formula stated in the SOFL literature. The tool does not invent missing operations from a catalog such as CRUD.

## 11. 操作粒度（功能不可再分）

第 2 节的结构原子只说明叶子过程的**谓词义务**已经闭合。刘少英的 SOFL 还要求分解停止在「一个足够简单、可以用 pre/post 完全说清的功能」上，但文献里的停止条件是定性判断，FSF 只检查**同一个**过程内部的场景遗漏。谓词写全了、名称仍是「维护学生」、正文只实现插入时，形式二义性可以是 0，需求仍然偏粗。操作粒度是对这一停止条件的可审计化，**不是**文献中的原公式，也**不是**按实体预置的操作目录。

### 11.1 变体从哪来

每个过程有一组变体，只来自三处：

- 作者已经写过的话：过程 `comment`、Informal 标题正文里的列举（`包括`、`以及`、顿号，或较短的 `and` / `or` 列举）。抽出来时状态为 `unresolved`。普通散文不拆。
- 谓词里已经写明的效果：闭集 `insert`（`union` / `dunion`）、`update`（`override` / `modify`）、`remove`（`diff`）、`query`（只读且有输出）、`batch`（顶层 comprehension）、多种并列时为 `mixed`，看不出来为 `opaque`。效果模式**不**生成「还应该有删除」这类义务。
- 审计步骤显式加入的变体。

关注词 `维护`、`管理`、`处理`、`负责`、`maintain`、`manage`、`handle` 只用来发现「名称或描述比单一效果更宽」（`nameEffectMismatch`）。它们不是要补齐的操作表。`转班` 这类没有关注词、也没有列举的过程不会被当成缺了一套 CRUD。

变体的归宿只有 `scenario`（同一触发的不同结局）、`child`（独立触发，必须落到分解目标模块里的子过程）、`waived`（须有理由）或仍为 `unresolved`。

### 11.2 操作原子与计数

叶子在下列条件**同时**成立时 `grainClosed`（操作原子还要求结构原子）：

- `ClassifyGrain` 为 `operation`（标成 `abstract` 的叶子不能签收）
- 没有 `unresolved` 变体，也没有找不到子过程的 `child`
- 没有 `nameEffectMismatch`；`mixed` 效果必须先 `decom`
- 若有变体被标成 `scenario`，其个数与推导出的功能场景数一致

`grainAmbiguity` 是当前义务个数，加上**未经** `ClassifyGrain`、`ResolveVariation` 或 `DecomposeProcess` 就从规格里消失的粘性义务（`ASFL_REFINE_002`）。粘性义务包括未分类叶子、抽象叶子、名称过宽、未决变体和 `mixed`。直接改 pre/post 或改名不能把这些计数清零。带 `decom` 的过程可以停留在关注点上；它的未决变体仍然计数，但「尚未分类」只计叶子。

`DeclareAtomic` 调用 `canDeclareAtomic`：结构原子与 `grainClosed` 缺一不可。因此形式五闸门全过、效果却只是 `insert` 的 `维护学生` 不能签收。收窄为单一操作时要改名，并用 `ResolveVariation`（`variationId=name-claim`，`disposition=waived`）记下原来的宽名称；列出的独立触发则标成 `child`，再 `DecomposeProcess`。工具不会补上文本里没写过的查询或批量。

### 11.3 受控迭代

Agent 读精化摘要，用澄清卡呈现**已经抽出**的变体，确认后提交 `ClassifyGrain` 或 `ResolveVariation`。澄清卡不负责发明操作。第一期不做开放域动词理解，也不证明父过程 post 被子过程复合。
